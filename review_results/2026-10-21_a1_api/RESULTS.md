# A1 (the real API in front of the answer engine): what was built and what the tests show (2026-10-21; owner's go: "Lets start with keep building the website")

Recourse branch `register-hooks-and-overlay`, commit `78b760a`, NOT on `main`; **full free suite after the last change: 94 run, 94 passed, 0 failed (8 live-model files not run);** nothing deployed; no live model was used (the sandbox has no Anthropic key), every test uses a stubbed model. Details of the design: `WEBSITE_DESIGN.md` sections 3, 5.1, 5.2.

## Built
- `progress.py` (live steps) and eleven one-line `_progress(...)` calls in `chat_assistant.py`: steps `scope`, `acts`, `sections` (only when a shelf section reached the material), `library`, `wider` (only when the wider search contributed), `write`, `register`, `checks`. With no listener set nothing runs and nothing changes (test: the result is byte for byte the same with and without a listener, and without a listener the Act lookup adds no work). Details are counts and Act names only; the module drops anything that is not a plain value, so no passage or question text can ride in a step (test uses a canary phrase).
- `cost_log.last_question()` (the cost of the question a thread just finished) so the API can return the cost of its answer.
- `api/ask.py`: `POST /api/ask` with header `X-API-Key`: server-sent events (start, step, result, error, done; a comment line every 15 s) when the caller sends `Accept: text/event-stream`, otherwise one JSON reply with the same content. FAILS CLOSED: without `API_ACCESS_TOKEN` the route answers 503, with a wrong key 401. Validation: 422 (empty, unknown audience, not JSON), 413 (over `API_MAX_QUESTION_CHARS`, default 6000), 429 with `Retry-After: 5` when the pool is full, 504 / `timeout` event after `API_ASK_TIMEOUT_SECONDS` (default 120). An engine failure reaches the caller as one fixed sentence (never the exception text, its type, or the question).
- `api/engine_adapter.py`: one question runs start to finish in ONE worker thread (`API_ENGINE_WORKERS`, default 4; waiting room twice that); the engine's result is made JSON-safe (sets, tuples, numpy values, NaN) and handed on whole, nothing dropped or renamed (plus a `text` alias of `response_text`, the cost and the time). `api/steps.py`: the plain-English line for each step, built only from the step's own details; unknown steps are not shown.
- `api/try_ask.py` (standard library only): asks one question from the command line and prints the steps as they arrive, then the answer, its state, cost and time; reads the key from the environment, never prints it.
- `api/openapi.json` (the front end's contract) with a test that fails if it drifts from the app.
- Tests (all free, offline): `test_progress.py` (26 checks), `test_api_ask.py` (59 checks incl. a real server process and the command-line helper), `test_api_concurrency.py` (19 checks), `test_api_health.py` (guard test, 13 checks).

## What the concurrency test shows (the real engine, stubbed model with random pauses, 16 questions that alternate: names the PC Act section 17 / plain, layman / lawyer)
Every question was run (1) alone in a fresh thread, (2) one after another on ONE reused worker thread, (3) 16 in parallel on 8 threads through the adapter, (4) 16 in parallel through HTTP with streaming, and (5) with a caller who leaves. In every case each result, each cost and each live-step list was IDENTICAL to the fresh-thread one; a question abandoned by its caller still finished, was released, and did not disturb the next question on that thread. **No leakage of Act, audience, notice, cost or steps was found.** What this does NOT prove: it ran with stubbed model and embedding calls, 16 questions, one set of switches (v3, shelf on, grounding warn), no wider search, no anchors, no follow-up folding; it is evidence, not a proof of thread safety. The shared caches (`act_shelf._STATE`, `act_directory._STATE`) are lock-protected by their authors; the daily-budget file has an in-process lock only, so ONE replica.

## A second finding, caught by reading the callers before the tests ran
The Streamlit page and the WhatsApp bot ALWAYS call the engine with `inline_domains={cheque_bounce, freeze, domestic_violence, ndps}`; my first adapter called it without them, so a cheque-bounce, bank-freeze, domestic-violence or NDPS question would have been redirected ("covered elsewhere") instead of answered, a parity break no stub test would have shown. Fixed: the adapter passes the same four topics (`engine_adapter.INLINE_DOMAINS`) and a test reads the sets out of `recourse_app.py` and `whatsapp_bot.py` and fails if the three ever differ.
