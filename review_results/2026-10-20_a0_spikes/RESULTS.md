# A0 spikes (2026-10-20): what was checked, how, and what it means for WEBSITE_DESIGN.md

Nothing here touches the live site. Scripts in this folder are the spike's (a local stand-in for Google's sign-in, a one-page Streamlit app, a Chromium driver); the values in `secrets.toml.example` are placeholders. To rerun: install `authlib` (not in the repo's requirements yet), start `fake_oidc.py`, run the page with `streamlit run`, set `AUTHLIB_INSECURE_TRANSPORT=1` (local http only).

## Spike 1: what Streamlit's login (`st.login`) gives the page. DONE, run end to end in a real browser (headless Chromium)
Against a local stand-in for Google (not Google itself), Streamlit 1.58.0 with Authlib 1.9.1:
- Sign-in worked. `st.user` held `sub`, `email`, `email_verified`, `name`, `iss`, `aud`, `exp`, `provider` [Certain for the stand-in; Google sends the same standard claims, [Likely]].
- With `expose_tokens = "id"` the page can read the provider's ID token (`st.user.tokens["id"]`).
- **The ID token goes stale while the person stays signed in.** With a 5-second token life, 12 seconds later after a reload the page was still signed in and the token's remaining life read -9 seconds. The installed Streamlit source has no refresh code (searched `refresh_token`, nothing). Streamlit's own login cookie lasts 30 days. Google ID tokens live about an hour [Likely]. So **forwarding the Google ID token to the API would fail after an hour; the design's own short-lived signed token (WEBSITE_DESIGN 1.3) is required, and it works**: the page minted a 5-minute HS256 token with `sub`, `email`, `jti`, audience `recourse-api` and verified it.
- `Authlib` is NOT in `requirements.txt` today (`streamlit[auth]` needs `Authlib>=1.3.2`; 1.9.1 installs). PyJWT is not pinned either. Both are added at A5, with the website's next deploy.
- Not tested: real Google (needs the owner's OAuth client), behaviour across a Streamlit redeploy (the cookie is signed with `cookie_secret`, so keeping that secret stable should keep people signed in [Likely]), behind Railway's proxy with https.

## Spike 2: a service of its own from the same repository, avoiding the website's `railway.json`. PART DONE; the Railway side needs the owner
From Railway's documentation and forum, via web search (the docs host is not reachable from the sandbox) [Likely, not tested on Railway]:
- Each service has a "config as code" file path setting in its Settings, an absolute path from the repository root (for example `/api/railway.api.json`); a config file overrides the dashboard values; the setting does not follow the Root Directory.
- A forum thread reports that the custom path was saved but ignored by the newer **Railpack** builder (the default for new services), which kept loading the root `/railway.json`; no staff confirmation found. A Dockerfile path (`RAILWAY_DOCKERFILE_PATH`) is the documented alternative, with reports that it is sometimes not honoured when a root `railway.json` exists.
- So the design keeps its three layers (own config file; Dockerfile fallback; healthcheck guard) and **this must be tried once on Railway**. Built for that: Recourse branch `register-hooks-and-overlay`, commit `57c89b1`: `api/main.py` (only `/api/health`, answers `{"role":"api",...}`), `api/railway.api.json` (start `uvicorn api.main:app`, healthcheck `/api/health`, one replica), `test_api_health.py` (11 checks: the API config never starts Streamlit, the root `railway.json` and `Procfile` are still the website's). It boots locally with the same command and answers. Nothing else is in `api/`; the engine is not touched.
- Owner's test on the STAGING project (see the action list in the reply of 2026-10-20): new service from the repo, branch `register-hooks-and-overlay`, Settings: config file path `/api/railway.api.json`; deploy; open `/api/health`. Pass = `{"role":"api"}`. A Streamlit-looking page or a failed healthcheck = the file was ignored; then try `RAILWAY_DOCKERFILE_PATH`, and tell Claude what the Deploy Logs say.

## Spike 3: private networking between Streamlit and the API. RESULT: DROPPED FROM THE PLAN
Railway's documentation says the private network is IPv6; a service that receives private calls must listen on IPv6 (`::`); the same documentation says some servers, uvicorn among them, do not handle both IPv4 and IPv6 on `::`; environments created after 16 October 2025 resolve to IPv4 and IPv6, older ones to IPv6 only [Likely]. The sandbox has no IPv6, so uvicorn's `::` behaviour could not be tested here. The owner's production environment may be older. Decision: **Streamlit calls the API over its public HTTPS address with the signed token** (the token is the protection, TLS is the transport). This removes one unknown at the cost of a little latency. Private networking can be added later as an optimisation.
